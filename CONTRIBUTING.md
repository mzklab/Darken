# How to help Darken

In short: **bugs and requests yes, pull requests no.**

## Bugs

The most useful thing you can do.

**If one window stayed bright** - the common case, and the one with the
fastest answer. Open that window and type `/dark probe`. It walks the
window with the same rules the darkening itself uses and names a verdict
for every texture in it: dims, content, forbidden by the engine,
protected by the engine, type skipped whole, deeper than the budget,
protected with the setting off. Twenty lines land in chat and the whole
list goes into the saved file. Point the cursor at one piece and type
`/dark probe mouse` to ask about that piece alone.

That output usually settles it without anyone guessing.

**For anything else**, the order is this:

1. In game, type `/dark report`. A handful of lines land in chat; the
   full detail goes into the saved variables.
2. Log out. That is what writes the file to disk - the game keeps saved
   variables in memory until then.
3. Open a [new issue](../../issues/new/choose), pick "Something is
   broken", and attach
   `WTF/Account/<account>/SavedVariables/Darken.lua`.
4. Add in your own words what you were doing and what you saw. One
   screenshot is worth ten paragraphs.

`/dark report`, `/dark probe` and `/dark scan` only read. Nothing on
screen changes when you run them.

**What the report holds.** The addon, contract and settings versions;
which parts of the interface this client actually has and which
subsystems therefore did nothing; the counters; what is registered. That
last one matters more than it looks: "the subsystem did nothing because
this client has no such frame" and "the subsystem is broken" look
identical from the outside and are one line apart in the report.

**What it also holds, so you know before you send it.** The file is your
whole saved-variables table, and the game keys profiles by character and
realm, so a `profileKeys` block near the end lists your characters.
Delete that block if you would rather not send it - nothing in the
report depends on it.

If the addon failed to load so badly that `/dark report` does nothing,
open the issue without it: the client version and the list of your other
addons typed by hand are still better than nothing.

## Feature requests

Also an issue. What helps most is not "add X" but **what you were trying
to do and how it ended**. The per-area strengths and the grey left on a
mob somebody else tapped both came out of accounts like that, not out of
a feature list.

## Pull requests

Not accepted; incoming ones are closed at once. This is not about the
quality of your change - the reason is different.

Darken is written in one style, and that style is not about indentation.
Every piece of code explains **why** it is the way it is: which breakage
produced it, what was tried before it and how that was worse. A good
part of the repository is those explanations, and the test suite is
written the same way - 8759 checks whose names read as sentences about
the behaviour rather than about the function.

A change without that breaks the one thing all of it was written for:
being able, six months later, to understand the decision without walking
the whole road to it again. Bringing somebody else's change into that
shape takes longer than writing it again, and refusing after a person
has spent an evening is worse than saying so in advance. So it is said
in advance.

**What to do instead.** Describe in an issue what needs fixing and why.
If you found the exact line, name it. That reaches the code faster than
a pull request.

## Building and testing

The test suite needs LuaJIT; the image tools need Python 3 with Pillow.
Neither is needed to play - only to work on the addon.

```
powershell tools/fetch-libs.ps1   fetch the libraries (they are not in the repo)
luajit tests/run.lua              run the test suite
python tools/make_branding.py     redraw the icon, the lockup and the in-game title
python tools/shots.py             build the store gallery from the raw captures
powershell tools/package.ps1      build the release archive
```

`tools/fetch-libs.ps1` comes first on a fresh clone: `Libs/` is not kept
in the repository, and without it the addon loads and silently does
nothing.

Unlike its neighbours Rack and Hive, Darken does ship third-party code:
Ace3, LibSharedMedia-3.0 and LibStub live under `Libs/` and keep their
own licences. Everything else in the tree is the author's, and the bar
textures and branding are generated by the tools above.

## Writing a module

Another addon can register with Darken and get a section in its settings
window. The contract is `Core/Api.lua` - one global object, with the
comments in that file saying what each door is for and why it is shaped
that way. The licence grants this explicitly (section 2.5): a module is
your work, distributed under terms of your own.

## Translations

A separate case, and here changes are taken. The tables live in
`Locale/` for the core and in `Features/<part>/Locale/` for each part,
written as "English key -> translation". Send the text in an issue, or
say you want a whole language, and we will sort it out.

English, Russian and Ukrainian exist today; a client of any other
language gets English.

## If you want to make your own thing

The licence (`LICENSE`) forbids forks and re-uploads, but the "ask
first" clause in it is not decoration: ask. The answer is usually yes.
